# mcp-guard 0.2.0 Design: Practical Local MCP Scanning

## Status

Draft for user review.

## Goal

0.2.0 turns mcp-guard from a single-file scanner into a practical local MCP safety check. A user should be able to run one command in a real development environment and find risky MCP configuration across common project and user-level locations without knowing every client-specific file path.

The release should still feel small and reliable: no network calls, no server execution, no package inspection, and no policy engine yet.

## User Outcomes

- A developer can run `mcp-guard scan --all` and scan known MCP configuration files for their current workspace and user profile.
- Existing `mcp-guard scan <path>` behavior remains compatible with 0.1.0.
- Multi-file results are readable in text mode and machine-readable in JSON mode.
- Secret values remain redacted in every output path.
- Documentation explains what locations are discovered, how exit codes work, and how to use the tool in CI.

## Non-Goals

- Do not execute MCP servers.
- Do not fetch remote MCP URLs.
- Do not inspect packages invoked through `npx`, `uvx`, Docker images, or other dynamic runners.
- Do not add SARIF, baselines, or long-term policy management in 0.2.0. These fit better in 0.3.0.
- Do not require a persistent project config file to use discovery.

## Scope

### 1. Auto-Discovery

Add a discovery layer that can produce scan targets from known MCP config locations.

The existing explicit path flow remains:

```bash
mcp-guard scan ./mcp.json
```

New discovery flow:

```bash
mcp-guard scan --all
mcp-guard scan --all --client cursor
mcp-guard scan --all --client vscode
mcp-guard scan --all --client claude-code
mcp-guard scan --all --client claude-desktop
mcp-guard scan --all --scope project
mcp-guard scan --all --scope user
mcp-guard scan --all --list-targets
```

Supported clients for 0.2.0:

| Client | Scope | Candidate path |
| --- | --- | --- |
| Cursor | Project | `.cursor/mcp.json` |
| Cursor | User | `~/.cursor/mcp.json` |
| VS Code | Project | `.vscode/mcp.json` |
| VS Code | User | Platform-specific VS Code user profile MCP config, resolved by a dedicated provider |
| Claude Code | Project | `.mcp.json` |
| Claude Code | User | `~/.claude.json` when it contains a supported MCP server map |
| Claude Desktop | User | Platform-specific `claude_desktop_config.json` or `config.json` candidate under the Claude app config directory |

Discovery must be conservative:

- Only scan files that exist and are readable.
- Missing files are not errors.
- Unsupported JSON shapes should produce a warning for that target and continue scanning other targets.
- Duplicate real paths should be scanned once, while preserving all matched labels in JSON metadata.
- User-home paths in messages should be redacted as `~`.

### 2. Aggregate Scan Result

Keep the current single-file `ScanResult` shape for `scan <path> --json`.

Add a new aggregate result for `scan --all --json`:

```ts
interface AggregateScanResult {
  schemaVersion: '2';
  targets: ScanTargetResult[];
  summary: {
    risk: Severity;
    targetsDiscovered: number;
    targetsScanned: number;
    serversScanned: number;
    findings: number;
  };
  findings: AggregateFinding[];
}
```

Each aggregate finding should include target metadata:

```ts
interface AggregateFinding extends Finding {
  target: {
    path: string;
    client: string;
    scope: 'project' | 'user';
  };
}
```

Text output should group by target first, then server:

```text
mcp-guard scan --all

Risk: CRITICAL
Targets scanned: 3
Servers scanned: 8
Findings: 12

Target: .cursor/mcp.json (cursor, project)
Server: github
  [HIGH] MCPG001 Secret-like environment variable
    ...
```

If no targets are found, exit 0 and print a clear warning:

```text
warning: no MCP configuration files found
```

### 3. Rule Coverage Updates

0.2.0 should improve real-client coverage without expanding the rule set too aggressively.

Required updates:

- Extend server normalization to preserve `headers`, `envFile`, and `type` fields from common MCP configs.
- Extend `MCPG001` to check secret-like keys in `headers` as well as `env`.
- Ensure `MCPG004` and `MCPG008` handle both `transport` and `type` when the config uses `http`, `sse`, or streamable HTTP terminology.
- Ensure all URL findings continue to redact userinfo, query strings, and paths.

Optional stretch if implementation stays small:

- Add an informational finding when `envFile` is present, explaining that secrets may be loaded from a file that mcp-guard does not inspect.

The stretch item should not block 0.2.0.

### 4. CLI Behavior

`scan <path>` stays unchanged.

`scan --all` changes the target argument from required to conditionally optional:

- `mcp-guard scan <path>` scans that path.
- `mcp-guard scan --all` discovers and scans known targets.
- `mcp-guard scan` without a path and without `--all` remains a usage error with exit code 2.
- `mcp-guard scan <path> --all` is a usage error with exit code 2 because explicit and discovery modes are mutually exclusive.

Existing options apply to both modes:

- `--json`
- `--fail-on <level>`
- `--quiet`
- `--no-color`

New discovery options:

- `--client <name>` filters discovery to one client.
- `--scope <project|user|all>` filters project/user discovery; default is `all`.
- `--list-targets` prints discovered targets and exits without scanning.

### 5. Architecture

Add discovery as a small independent subsystem.

Proposed modules:

```text
src/discovery/
  types.ts
  candidatePaths.ts
  discoverConfigs.ts
  scanDiscoveredTargets.ts
```

Responsibilities:

- `candidatePaths.ts`: builds candidate paths from a workspace directory, home directory, platform, client filter, and scope filter.
- `discoverConfigs.ts`: checks file existence/readability, deduplicates real paths, and returns target metadata.
- `scanDiscoveredTargets.ts`: loads each target, runs the existing scanner, aggregates warnings, findings, and summary data.
- Existing `loadConfig`, `normalizeServers`, rule modules, and reporters remain the core scanning path.

Reporter additions:

```text
src/reporters/
  aggregateJsonReporter.ts
  aggregateTextReporter.ts
```

The aggregate reporters should reuse existing redaction helpers and formatting conventions.

### 6. Testing

Add focused tests around the new behavior.

Discovery tests:

- Candidate paths for Windows, macOS, and Linux are generated from injected home/workspace/platform values.
- Missing candidate files are ignored.
- Existing candidate files become scan targets.
- Duplicate real paths are deduplicated.
- Client and scope filters work.

Aggregate scan tests:

- Multiple configs are scanned and summarized.
- One malformed or unsupported config emits a warning but does not stop other targets.
- Aggregate JSON uses `schemaVersion: "2"`.
- Findings include target metadata.
- Secret values from `env` and `headers` never appear in text or JSON output.

CLI tests:

- `scan --all` works.
- `scan --all --json` returns aggregate JSON.
- `scan --all --fail-on high` exits 1 when any target has a high or critical finding.
- `scan --all --list-targets` lists targets and does not scan.
- `scan` without path and without `--all` exits 2.
- `scan <path> --all` exits 2.
- Existing 0.1.0 CLI tests continue to pass.

### 7. Documentation

Update README with:

- `scan --all` examples.
- A table of discovered clients and locations.
- Explanation of project vs user scope.
- CI examples using explicit path and discovery mode.
- JSON output note: single-file scans keep schema version 1; discovery scans use aggregate schema version 2.

Update CHANGELOG under `[Unreleased]`.

### 8. Acceptance Criteria

0.2.0 is ready when:

- `npm run typecheck`, `npm test`, and `npm run build` pass locally.
- CI passes on Node 20 and Node 22.
- `mcp-guard scan <path>` remains backward compatible with 0.1.0 behavior.
- `mcp-guard scan --all` scans discovered MCP configs and returns exit code 0 when no threshold is tripped.
- `mcp-guard scan --all --fail-on high` returns exit code 1 when any target has high or critical findings.
- Aggregate JSON includes target metadata for every finding.
- Text and JSON outputs do not leak secret values from `env` or `headers`.
- README documents the new discovery behavior clearly.

## Risks And Mitigations

Known MCP client locations can change. Keep discovery providers small and table-driven so path updates are isolated.

User-level config formats may include structures beyond top-level `mcpServers` or `servers`. 0.2.0 should warn on unsupported shapes instead of trying to infer everything.

Discovery can create false confidence if a client stores MCP servers outside known files. README should call discovery "known common locations" rather than exhaustive machine auditing.
